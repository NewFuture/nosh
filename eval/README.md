# 真实模型评测

Linux/WSL 上的本地评测，不进入每个 PR 的真实模型 CI。需要支持 pidfd 的 Linux 内核（5.3+）、Python 3.11+、`git`、`bash`、`python3`、`tar`、`ss`，以及构建好的 nosh 和已经下载的模型。没有第三方 Python 依赖。清理时用 pidfd 固定进程身份，避免 PID 重用时误发信号。

## 一条评测命令

先按根 README 构建 release 二进制并安装模型；模型准备不计入评测。以下命令在 **Linux/WSL 的仓库根目录**执行：

```bash
python3 -m eval.run --model-path "$HOME/.local/share/nosh/models/minicpm5-2b-q4_k_m"
```

它会为 MVP 的 10 个场景各运行固定 seeds `[0, 1, 2, 3, 4]`，逐次重建夹具、处理审批、生成 `eval/results/<run-id>/report.json` 和 `report.md`。完整一轮是 50 次场景试验，其中 5 次是无需模型的拼写纠错，不是 50 个不同任务。模型、下载、构建不自动安装；缺少前置条件会明确报错。

```bash
# 选择场景和 seed，使用另一个构建
python3 -m eval.run --model-path MODEL_DIR --binary NOSH_BINARY \
  --scenario rename-files --scenario persistent-cwd --seeds 0 1

# 同构建、同机器全量双跑；共 100 次场景试验
python3 -m eval.run --model-path MODEL_DIR --repeat 2

# 与上一次 JSON 报告按场景、seed、重复序号配对
python3 -m eval.run --model-path MODEL_DIR --compare PREVIOUS_REPORT_JSON

# 明确选择旧构建：允许无法观测的指标为 null，而不是伪造指标
python3 -m eval.run --model-path MODEL_DIR --binary OLD_NOSH --legacy \
  --build-info BUILD_JSON
```

`--output` 指定一个尚不存在的输出目录；现有结果不会被覆盖。`--label` 只设置报告名称，不是构建来源证明。`--threads` 默认 8，Rayon 固定 1；`--timeout` 默认使用场景集的 240 秒上限。退出码 0 表示所选试验全部通过，1 表示判定失败或双跑不一致，2 表示基础设施/观测错误，130 表示中断。失败也保留报告，未完成的试验不从统计分母中移除。

## 场景与审批

[`scenarios.json`](scenarios.json) 包含入口、输入、夹具、审批策略、判定器和全局 seed/超时配置。REPL 输入原样发送，支持 `#`、无前缀自然语言及场景内多轮交互；`-a` 的 git 附件由实际 git 命令生成，`-s` 直接调用二进制。

| 场景 | 判定核心 |
|---|---|
| 大文件 | 回答中的前三个文件及顺序与实际字节数一致 |
| 端口 | 回答指出本次监听进程的名称和真实 PID |
| 代码行数 | 各语言行数正确，出现的总数也正确 |
| 改名 | 四个文件完成改名、内容不变、已有 md 文件保留，并发生真实审批 |
| 中文问题 | 中文回答准确列出三个 Python 文件 |
| 本地纠错 | 修正结果留在编辑行，未自动执行、未调用模型 |
| 失败分析 | 真实运行 broken.py 失败后，指出缺少 config.json 并给出修复方式 |
| git 摘要 | 固定八个提交中的组件与关键事实对应正确 |
| 命令建议 | 只输出建议、未执行；受限验证后归档文件及内容正确 |
| cwd 连续性 | agent 操作后，在同一 shell 用实际 `pwd -P` 验证 |

判定只使用最终回答及真实状态，不把输入回显、工具输出中的正确答案算作模型答对；中间回答保留在原始日志/生成记录中。事实提取是保守、确定性的规则，不使用另一个模型打分：例如语言行数需要带语言名称的明确计数或有 Lines/LOC/行数表头的表格。散文中的 `Python: 3 files, 15 lines` 读取与 lines/LOC/行关联的数值 15，允许文件数在前，不会把文件数或下一种语言的计数当成该语言的行数；无单位时仅接受 `Python: 15` 这种纯数值形式。无法解析会说明原因，不会按“差不多正确”放行。新夹具是按 MVP 场景意图重建的，并非恢复了未入库旧夹具的每个字节。

Python 文件判定同时检查分类方向：把预期 `.py` 文件列为“非 Python”也算失败。失败分析不仅需要指出缺少 `config.json`，还要包含创建文件、修正路径、切换目录等明确修复动作；仅描述当前目录或相对路径中缺少文件不算给出了修复方法。

列表和小计按明确作用域判定：大文件排名不合并另起说明的参考列表，但排名本身多出第四项或顺序错误仍失败。语言小计只有在列出的文件完整、不重叠、每段恰有一个行数小计时才相加，所有总体数字仍需正确。明确的“目录”概览不视为 Python 分类；其后的 Python 列表必须独立包含全部预期文件，不能靠概览补齐遗漏，也不能把 shell 文件列入 Python 列表。

默认审批模式保持 `confirm`。只有声明为改名/cwd 的场景会对有限、可验证的命令子集回答 `y` 或危险确认 `yes`：

- 改名接受 `for f in *.txt; do mv "$f" "${f%.txt}.md"; done` 一类固定循环，或对夹具内明确源/目标的 `mv` 列表，包含带空格的文件名；允许先 `cd` 到该夹具根目录以及末尾只读 `ls`。
- cwd 接受切换到夹具的 `data`，可跟随 `&& ls` 或 `; ls` 和常见只读选项。
- 其他命令或受保护读取一律拒绝。报告保存实际卡片、命令和答复，区分模型失败与评测审批策略的限制，不使用 auto/yolo 或“本会话同类放行”。

`-s` 的验证器只执行经过严格解析的 tar 参数，不将任意模型输出交给 shell 执行。支持 `tar -czf logs.tar.gz logs`、`cd logs && tar -czvf ../logs.tar.gz .`、`tar -czf logs.tar.gz -C logs .` 等形式；额外命令、展开、重定向、外部路径和危险 tar 选项不执行，明确判为未通过。

## 隔离与复现口径

每个场景/seed 是新进程，只有场景内部共享会话；这是冷会话/KV 缓存，不保证操作系统页缓存也是冷的，不与 MVP 连续交互的热会话混比。设置独立 HOME/NOSH_HOME、固定 locale/TZ/PATH、终端大小、模型上下文和线程配置；显式使用 `--norc --offline --no-download --seed`。工作目录默认为系统临时目录中的 `nosh-eval-<uid>`，通过所有权标记和独占锁防止并发覆盖。自定义 `--work-dir` 必须在支持 Unix 私有权限的文件系统上（WSL 建议使用 Linux 的临时目录），属于当前用户且权限为 0700，位于现有仓库和 NOSH.md 祖先之外，不能包含二进制、模型或报告。

每次重建文件内容、大小、权限和 mtime，git 历史固定作者、时间和提交顺序。端口夹具只监听 loopback 8080，等到实际绑定成功才开始测试；已有服务占用该端口时明确报错，绝不替换或终止该服务。只回收本次创建的进程、监听器和工作子目录。

**临时目录不是操作系统安全沙箱。** 建议在评测专用 Linux 用户或受限容器中运行，勿在包含敏感数据的生产会话中执行模型评测。所有日志均在本地，只有选定的基线结果入库；不提交个人配置或模型权重。

“重跑一致”指同构建、同机器、同 seed 的**自动判定和最终状态一致**。回答、工具轨迹和观测到的输入差异另外列出，性能数值不要求逐值相同。当前 prompt 含实际时刻，最近命令/工具响应含耗时，端口场景的 PID 也会变化；固定 seed 不会固定这些输入。报告不能将差异直接归为推理随机性，也不会用重试到通过替代原始失败。单轮报告明确标注复现尚未测量。

## 指标与观测协议

运行器显式设置 `NOSH_EVAL_TRACE=<私有文件>`，在 CLI 装配处包装实际 ChatEngine，记录版本化 JSONL：session 参数、追加输入、生成结果、工具调用及原始 Usage。三个入口均可观测，`-s` 的 stdout 仍只有命令。没有设置该变量时，不新增日志、不改变采样或任务行为；文件创建/写入失败会暴露为错误。日志只接受普通私有文件（Unix 不跟随符号链接，权限不得向组/其他用户开放），写入位于引擎 Usage 计时之外。它是接口层记录，不是完整 token 流；未包含所有内部保留的 assistant token，所以 `inputs_changed=false` 不证明完整 token prompt 相同。

| 指标 | 口径 |
|---|---|
| 通过率 | 通过数 / 所选场景的计划试验数；错误、超时、未完成不从分母消失 |
| 步数 | engine step 次数，含总结步骤，不等同于命令数；本地纠错为 0 |
| 确认次数 | 实际审批请求次数，拒绝也计数 |
| TTFT | 首步 `Usage.ttft_secs`，不含模型装载；不会用首个 stdout 或总耗时替代 |
| 总耗时 | 进程启动至退出，含加载、交互和退出，排除夹具生成及建议验证；另存可得的任务/加载耗时 |
| RSS | 逐个 nosh 进程的 Linux wait4 峰值，统一 MiB；包括内核对已等待后代的统计，不是进程树 RSS 求和，监听器/验证器另起进程 |

Markdown 的步数/确认为均值，延迟/耗时为中位数，RSS 为最大值；JSON 保存逐次数据与有效样本数。失败运行的可用指标也参与统计，避免只保留成功样本。五个 seed 不是显著性检验。默认 agent temperature 为 1.0，建议模式为 0.7，原始实际参数在新观测报告中保存。

显式 `--legacy` 用于未改动的旧 main：REPL 复用 NOSH_STATS，`-a` 复用 JSONL；成功的 `-s` 按其单步 CLI 契约记一步，真实 TTFT 不可测，写 `null` 和原因。旧 REPL 的 TTFT/任务耗时分别只有 0.01/0.1 秒显示精度，完整引擎输入/工具轨迹也不可观测。新模式缺失事件时不会静默降级。

每份报告记录二进制/模型/tokenizer/场景/运行器哈希、主机、工具版本、有效设置、seed、回答原文及证据。运行器同时保留物理文件哈希和统一 UTF-8/LF 的源文件内容哈希，比较时优先用后者，避免 Windows 工作树的 CRLF 制造代码差异；若追加 `harness_revision`，需先将运行时源码指纹与该提交核对。`--build-info` 接受 `schema_version: 1`、`source_revision`（完整 SHA）、`binary_sha256` 的构建记录，二进制哈希必须匹配；可附 `source_ref`、`source_clean`、源码归档哈希、构建命令和工具链版本。来源是该构建记录的声明，不是运行器用当前 checkout HEAD 猜出来的；未提供时明确标注来源未验证。

版本比较检查数据集、判定器、模型、参数、环境和观测模式。不同条件仍显示配对原始差值，但明确警告不是受控的回归结论，不跨缺失指标造数。JSON 保留全部配对项和未配对计数。

## 基线生命周期

当前 main `7c57a88641d634f84dc190afafcee3cdb1813c1f` 的 [legacy 实测](baselines/main-7c57a88/report.md) 使用从该 SHA 的干净源码归档构建并预先保留的二进制。该报告是**有限观测的原始 main 实测**，不是补齐所有指标、已验证双跑一致的正式基线。

观测支持合入 main 后，在同一机器固定新的完整 main SHA、保存 release 二进制和构建清单，使用 `--repeat 2` 全量执行，把 JSON、Markdown 和构建来源一起入库。先前基线保留，不覆盖；报告提交可晚于被测提交，但必须准确标注被测二进制。完成这一步之前，#3 的完整 main 基线验收仍待完成，不把功能分支实测冒充 main。

## 无模型自测

```bash
python3 -m unittest discover -s eval -v
cargo test -p nosh-cli --locked
```

Python 自测用固定夹具、正反例和脚本化 PTY/CLI 子进程覆盖驱动、审批、超时、清理、判定和报告；Rust 回归覆盖观测转发及错误。它们可以进入现有 CI，但不能替代真实模型基线。`eval/results`、大日志和 Python 缓存忽略入库。
