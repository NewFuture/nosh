# 真实模型评测

Linux/WSL 上的本地评测，不进入每个 PR 的真实模型 CI。需要支持 pidfd 的 Linux 内核（5.3+）、Python 3.11+、`git`、`bash`、`python3`、`tar`、`ss`，以及构建好的 nosh 和已经下载的模型。完整场景集还需要 Cargo、rustc、C 链接器（`cc`）、Node.js 22+ 和 npm；只选择原有场景时不要求这些新增工具。没有第三方 Python 依赖。清理时用 pidfd 固定进程身份，避免 PID 重用时误发信号。

## 一条评测命令

先按根 README 构建 release 二进制并安装模型；模型准备不计入评测。以下命令在 **Linux/WSL 的仓库根目录**执行：

```bash
python3 -m eval.run --model-path "$HOME/.local/share/nosh/models/minicpm5-2b-q4_k_m"
```

它会为 **25 个场景**各运行固定 seeds `[0, 1, 2, 3, 4]`，逐次重建夹具、处理审批、生成 `eval/results/<run-id>/report.json` 和 `report.md`。完整一轮是 **125 次**场景试验，其中 120 次真实模型任务、5 次无需模型的拼写纠错，不是 125 个不同任务。原有 10 个任务保留，新增 15 个真实项目/中文/失败求助场景。模型和工具链不会自动下载或安装；缺少前置条件会明确报错。

工具预检按所选场景执行并记录真实可执行文件、版本与 SHA-256。基础 shell 工具优先使用系统位置，新增编译/Node 工具遵循启动运行器的 PATH；使用独立安装的 Node 时，先把其 `bin` 目录加入 PATH。Rustup shim 会解析为实际工具链二进制，再通过每次试验的私有 `HOME/bin` 符号链接接入受控 PATH，避免切换 HOME 后找不到编译器。请提前准备工具链；项目夹具不需要 `npm install`、pip 或 Cargo 外部依赖。

```bash
# 选择场景和 seed，使用另一个构建
python3 -m eval.run --model-path MODEL_DIR --binary NOSH_BINARY \
  --scenario rename-files --scenario persistent-cwd --seeds 0 1

# 同构建、同机器全量双跑；共 250 次场景试验
python3 -m eval.run --model-path MODEL_DIR --repeat 2

# 与上一次 JSON 报告按场景、seed、重复序号配对
python3 -m eval.run --model-path MODEL_DIR --compare PREVIOUS_REPORT_JSON

# 明确选择旧构建：允许无法观测的指标为 null，而不是伪造指标
python3 -m eval.run --model-path MODEL_DIR --binary OLD_NOSH --legacy \
  --build-info BUILD_JSON --scenario largest-files
```

`--output` 指定一个尚不存在的输出目录；现有结果不会被覆盖。`--label` 只设置报告名称，不是构建来源证明。`--threads` 默认 8，Rayon 固定 1；`--timeout` 默认使用场景集的 240 秒上限。退出码 0 表示所选试验全部通过，1 表示判定失败或双跑不一致，2 表示基础设施/观测错误，130 表示中断。失败也保留报告，未完成的试验不从统计分母中移除。

## 手动 GitHub Actions 基线

本机资源不可用时，可以在独立的 GitHub-hosted Ubuntu runner 上执行，不占用本地 CPU/RAM：

```bash
gh workflow run ci.yml --repo NewFuture/nosh --ref EVALUATOR_BRANCH \
  -f evaluation=true -f source_revision=FULL_MAIN_SHA
```

`source_revision` 必须是 main 上的完整提交 SHA；留空时在作业开始固定当时的 main。工作流将该提交归档到隔离目录构建，模型由独立准备步骤显式下载并校验，然后以 **2 个推理线程、Rayon 1、25 × 5 × 2** 串行采样。所用运行器来自 `--ref` 的提交，报告会核对其源码指纹后分别记录 main 与运行器来源。

只有手动设置 `evaluation=true` 才运行真实模型；普通 push/PR 和默认手动 CI 仍只运行原有测试。评测与常规 CI 使用不同 concurrency group，不会因后续代码 push 自动取消正在采样的评测。完整采样且没有运行器错误时，工作流可以成功，即使模型任务或双跑一致性未通过；原始退出码、失败样本和部分结果均保存在 `evaluation-<run-id>-<attempt>` artifact，工作流绿色不表示模型通过率 100%。基线正式入库前仍需核对全部 250 个身份、来源和失败原因。

## 场景与审批

[`scenarios.json`](scenarios.json) 使用 v2 契约，包含入口、输入、夹具、审批策略、判定器、体验门槛和全局 seed/超时配置；运行器仍读取 v1 场景。REPL 输入原样发送，支持 `#`、无前缀自然语言及场景内多轮交互；`-a` 的 git 附件由实际 git 命令生成，`-s` 直接调用二进制。每轮 `completions` 显式声明 agent、失败的 shell 命令或本地纠错；失败命令必须实际出现声明的退出码及诊断，再发送求助，不用额外探针覆盖“上一条失败命令”。

保留的 MVP 任务：

| 场景 | 判定核心 |
|---|---|
| 大文件 | 回答中的前三个文件及顺序与实际字节数一致 |
| 端口 | 回答指出本次监听进程的名称和真实 PID |
| 代码行数 | 各语言行数正确，出现的总数也正确 |
| 改名 | 四个文件完成改名、内容不变、已有 md 文件保留，并发生真实审批 |
| 中文问题 | 中文回答准确列出三个 Python 文件 |
| 本地纠错 | 修正结果留在编辑行，未自动执行、未调用模型 |
| 失败分析 | 真实运行 broken.py 失败后，指出缺少 config.json 并给出修复方式 |
| git 摘要 | 固定八个提交中的组件与关键事实对应正确 |
| 命令建议 | 只输出建议、未执行；受限验证后归档文件及内容正确 |
| cwd 连续性 | agent 操作后，在同一 shell 用实际 `pwd -P` 验证 |

新增场景：

### 体验门槛与证据

v2 的 `expect` 必须声明 `max_steps`、`max_confirmations`、`response_language`（`zh`/`any`/`not_applicable`）、`final_question`（`forbid`/`require`/`not_applicable`）。非法组合或缺失配置直接报错。步数与确认次数等于上限时通过，超出即失败；拒绝的审批也计数。旧场景的具体门槛也保存在场景文件中。门槛应在正式采样前冻结，不能因模型表现不佳而放宽。

所有适用的事实/最终状态和体验检查都通过，试验才通过。两类结果及实际值、上限、失败原因分别记录。新增执行类判定关联 native trace 中的工具调用和结果，区分成功、失败、拒绝和跳过；只有“已完成”的回答、未执行的工具调用、已存在的产物或只编译不跑测试都不能过关。新增判定要求 native 观测，与 `--legacy` 组合会在启动前拒绝，不静默改成只看回答。

中文检查和收尾检查是可复核的确定性启发式，不使用另一个模型：从最终回答中去掉代码、引用诊断、路径/URL、版本号与技术工具名，中文正文至少两个汉字，且汉字数大于残余拉丁词数。不能靠路径里含中文或英文长文末尾附两个汉字充数。收尾检查末段疑问和“你想让我…/要不要…/Would you like…/Shall I…”等继续确认表达，不把代码中的问号当作追问。只有歧义对照要求提出澄清；本地纠错和 `-s` 纯命令输出的语言/收尾标为不适用。启发式仍有语言边界，JSON 保留抽取正文、统计和判定，便于复核。

判定只使用最终回答及真实状态，不把输入回显、工具输出中的正确答案算作模型答对；中间回答保留在原始日志/生成记录中。事实提取是保守、确定性的规则，不使用另一个模型打分：例如语言行数需要带语言名称的明确计数或有 Lines/LOC/行数表头的表格。散文中的 `Python: 3 files, 15 lines` 读取与 lines/LOC/行关联的数值 15，允许文件数在前，不会把文件数或下一种语言的计数当成该语言的行数；无单位时仅接受 `Python: 15` 这种纯数值形式。无法解析会说明原因，不会按“差不多正确”放行。新夹具是按 MVP 场景意图重建的，并非恢复了未入库旧夹具的每个字节。

Python 文件判定同时检查分类方向：把预期 `.py` 文件列为“非 Python”也算失败。失败分析不仅需要指出缺少 `config.json`，还要包含创建文件、修正路径、切换目录等明确修复动作；仅描述当前目录或相对路径中缺少文件不算给出了修复方法。

列表和小计按明确作用域判定：大文件排名不合并明确标为较小文件的参考列表，但更正后的排名、额外排名项及错误顺序仍需检查，不能靠任意说明段落隐藏。声明了语言小计时，只有列出的文件完整、不重叠、每段恰有一个行数小计才相加；未声明分节小计时，仍按明确的总体语言计数判定，所有总体数字均需正确。明确的“目录”概览不视为 Python 分类；其后的 Python 列表必须独立包含全部预期文件，不能靠概览补齐遗漏，也不能把 shell 文件列入 Python 列表。

默认审批模式保持 `confirm`。只有场景声明授权的有限、可验证命令子集会收到 `y` 或危险确认 `yes`：

- 改名接受 `for f in *.txt; do mv "$f" "${f%.txt}.md"; done` 一类固定循环，或对夹具内明确源/目标的 `mv` 列表，包含带空格的文件名；允许先 `cd` 到该夹具根目录以及末尾只读 `ls`。
- cwd 接受切换到夹具的 `data`，可跟随 `&& ls` 或 `; ls` 和常见只读选项。
- 项目场景只批准声明的 Cargo build/test/clean、已知 npm 脚本或完整 unittest 命令；可先 `cd` 到夹具根目录，或组合有限的 pwd、ls、读取已知源码的 cat。脚本/源码必须仍与夹具一致，不放行替换脚本、其他 manifest、任意解释器代码、额外写命令、管道或任意重定向。
- 提交只批准受限的 git add/commit，不能 amend、push 或提交夹具之外的路径；清理只批准 cargo clean 或指向夹具内非符号链接 target 的有限 rm 形式。
- 其他命令或受保护读取一律拒绝。报告保存实际卡片、命令和答复，区分模型失败与评测审批策略的限制，不使用 auto/yolo 或“本会话同类放行”。

`-s` 的验证器只执行经过严格解析的 tar 参数，不将任意模型输出交给 shell 执行。支持 `tar -czf logs.tar.gz logs`、`cd logs && tar -czvf ../logs.tar.gz .`、`tar -czf logs.tar.gz -C logs .` 等形式；额外命令、展开、重定向、外部路径和危险 tar 选项不执行，明确判为未通过。

## 隔离与复现口径

每个场景/seed 是新进程，只有场景内部共享会话；这是冷会话/KV 缓存，不保证操作系统页缓存也是冷的，不与 MVP 连续交互的热会话混比。设置独立 HOME/NOSH_HOME、固定 locale/TZ/PATH、终端大小、模型上下文和线程配置；显式使用 `--norc --offline --no-download --seed`。工作目录默认为系统临时目录中的 `nosh-eval-<uid>`，通过所有权标记和独占锁防止并发覆盖。自定义 `--work-dir` 必须在支持 Unix 私有权限的文件系统上（WSL 建议使用 Linux 的临时目录），属于当前用户且权限为 0700，位于现有仓库和 NOSH.md 祖先之外，不能包含二进制、模型或报告。

每次重建文件内容、大小、权限和 mtime，git 历史固定作者、时间和提交顺序。Cargo/npm 使用私有缓存和离线配置，Rust 夹具只用一个构建 job 且关闭 incremental。端口夹具只监听 loopback 8080，等到实际绑定成功才开始测试；已有服务占用该端口时明确报错，绝不替换或终止该服务。任务结束先记录自有监听器存活状态，再回收。只回收本次创建的进程、监听器和工作子目录。

构建/测试允许声明范围内的编译器产物，不允许改源码、测试、配置或新增无关路径。新夹具的稳定最终状态保留受保护文件和产物路径类别，忽略已识别编译缓存的字节/哈希后缀变化；原始文件快照与执行证据仍保留，未知产物不能借整个 target 目录的忽略规则隐藏。准备、独立产物验证器和普通前置失败命令不算 agent 步数。

**临时目录不是操作系统安全沙箱。** 建议在评测专用 Linux 用户或受限容器中运行，勿在包含敏感数据的生产会话中执行模型评测。所有日志均在本地，只有选定的基线结果入库；不提交个人配置或模型权重。

“重跑一致”指同构建、同机器、同 seed 的**自动判定和最终状态一致**。回答、工具轨迹和观测到的输入差异另外列出，性能数值不要求逐值相同。当前 prompt 含实际时刻，最近命令/工具响应含耗时，端口场景的 PID 也会变化；固定 seed 不会固定这些输入。报告不能将差异直接归为推理随机性，也不会用重试到通过替代原始失败。单轮报告明确标注复现尚未测量。

## 指标与观测协议

运行器显式设置 `NOSH_EVAL_TRACE=<私有文件>`，在 CLI 装配处包装实际 ChatEngine，记录版本化 JSONL：session 参数、追加输入、生成结果、工具调用及原始 Usage。三个入口均可观测，`-s` 的 stdout 仍只有命令。没有设置该变量时，不新增日志、不改变采样或任务行为；文件创建/写入失败会暴露为错误。日志只接受普通私有文件（Unix 不跟随符号链接，权限不得向组/其他用户开放），写入位于引擎 Usage 计时之外。它是接口层记录，不是完整 token 流；未包含所有内部保留的 assistant token，所以 `inputs_changed=false` 不证明完整 token prompt 相同。

| 指标 | 口径 |
|---|---|
| 通过率 | 通过数 / 所选场景的计划试验数；错误、超时、未完成不从分母消失 |
| 步数 | engine step 次数，含总结步骤，不等同于命令数；本地纠错为 0 |
| 确认次数 | 实际审批请求次数，拒绝也计数 |
| TTFT | 首步 `Usage.ttft_secs`，不含模型装载；不会用首个 stdout 或总耗时替代 |
| 总耗时 | 进程启动至退出，含加载、交互和退出，排除夹具生成及建议验证；另存可得的任务/加载耗时 |
| RSS | 逐个 nosh 进程的 Linux wait4 峰值，统一 MiB；包括内核对已等待后代的统计，不是进程树 RSS 求和，监听器/验证器另起进程 |

Markdown 的步数/确认为均值，延迟/耗时为中位数，RSS 为最大值；JSON 保存逐次数据与有效样本数。v2 同时汇总全部、原 10 个、新 15 个、模型任务和本地纠错，均值按逐次有效样本计算，不对各场景均值简单再平均。失败运行的可用指标也参与统计，避免只保留成功样本。缺少必须的观测不当作 0；普通 shell 返回而未进入预期 agent、预期失败却成功属于场景失败，损坏 trace/超时等属于观测或基础设施错误。五个 seed 不是显著性检验。默认 agent temperature 为 1.0；无工具建议模式也使用传入的采样设置（默认 1.0），历史正式基线的建议模式为 0.7，比较时必须注明此差异。原始实际参数在新观测报告中保存。

显式 `--legacy` 用于未改动的旧 main：REPL 复用 NOSH_STATS，`-a` 复用 JSONL；成功的 `-s` 按其单步 CLI 契约记一步，真实 TTFT 不可测，写 `null` 和原因。旧 REPL 的 TTFT/任务耗时分别只有 0.01/0.1 秒显示精度，完整引擎输入/工具轨迹也不可观测。新模式缺失事件时不会静默降级。

每份报告记录二进制/模型/tokenizer/场景/运行器哈希、主机、工具版本、有效设置、seed、回答原文及证据。运行器同时保留物理文件哈希和统一 UTF-8/LF 的源文件内容哈希，比较时优先用后者，避免 Windows 工作树的 CRLF 制造代码差异；若追加 `harness_revision`，需先将运行时源码指纹与该提交核对。`--build-info` 接受 `schema_version: 1`、`source_revision`（完整 SHA）、`binary_sha256` 的构建记录，二进制哈希必须匹配；可附 `source_ref`、`source_clean`、源码归档哈希、构建命令和工具链版本。来源是该构建记录的声明，不是运行器用当前 checkout HEAD 猜出来的；未提供时明确标注来源未验证。

版本比较检查数据集、判定器、模型、参数、环境、工具链和观测模式。v2 仍可读取 v1 报告；旧报告没有体验判定，不补填成功，旧版报告再生成路径保留。不同条件仍显示配对原始差值，但明确警告不是受控的回归结论，不跨缺失指标造数。JSON 保留全部配对项和未配对计数。

## 基线生命周期

**25 场景扩充基线尚未采集。** 目标是在精确、干净的 main 构建上串行运行 `--repeat 2`，记录 250 次结果及 125 对一致性；模型任务为 240 次、本地纠错为 10 次。运行前冻结 main SHA、裁判/场景、模型及工具链，并保存与二进制哈希匹配的 build-info。使用新的基线目录，不覆盖以下历史结果，不重抽失败 seed。场景集扩充和体验门槛改变后，通过率不能与旧 10 场景直接作受控比较。

历史 main `7c57a88641d634f84dc190afafcee3cdb1813c1f` 的 [legacy 实测](baselines/main-7c57a88/report.md) 是 36/50 通过、14 失败、0 运行器错误，使用该 SHA 的干净源码归档构建并预先保留的二进制。该版本化记录保持不变，是**有限观测的原始 main 实测**，不是原生观测的双跑正式基线。

观测支持经 #13 合入后，已在同一 WSL Ubuntu 机器、同一模型上完成 main **`4f602ab8d95d046162adb7d4b202ddf6d3e20bea`** 的[原生观测基线](baselines/main-4f602ab/report.md)：10 场景 × seeds `[0,1,2,3,4]` × 2 轮，单个串行 campaign，共 100 次，含 10 次本地纠错。精确干净源码在修改前隔离构建为 release，并用 [schema-v1 build-info](baselines/main-4f602ab/build-info.json) 核对二进制；报告提交和判定器修复不改变被测 main SHA。

原始结果 **70 通过 / 30 失败 / 0 错误**；修复三类有明确证据的列表/小计作用域误拒后，仅对原始观测确定性重评为 **73 / 27 / 0**，无缺失、无重新采样。其中真实模型试验 **63/90** 通过，本地纠错 **10/10** 通过；73% 是全部试验的通过率，不是模型任务通过率。每条记录保存 `original_judgment`，原始 JSON/Markdown 可逐字节重建，输入、回答、指标、审批和最终状态的摘要不变。[来源清单](baselines/main-4f602ab/provenance.json)和[逐项分析](baselines/main-4f602ab/analysis.md)保留原始哈希、全部变更及复现限制。

**基线已记录，#3 的判定复现验收尚未满足。** 50/50 对最终状态相同，但判定加状态仅 45/50 一致（原始为 44/50）；剩余差异为行数 seed 2、失败分析 seeds 0/3、归档建议 seeds 1/3。45/45 模型配对的初始接口输入含不同任务时间，其中一对还有不同的最近命令耗时；后续也可包含工具耗时、监听 PID 和目录时间差异，不能据此断言推理数值不确定性。`-s` 的真实 TTFT 已有 10/10 样本，中位数 2.12 s；90 次模型试验的 TTFT 中位数 4.90 s，全部 100 次进程总耗时中位数 16.93 s，wait4 峰值 RSS 最大 2423.92 MiB。本地纠错 TTFT 为 N/A；这些是冷会话而非冷操作系统页缓存数据，不与旧手工/legacy 数字直接作受控回归比较。

## 无模型自测

```bash
python3 -m unittest discover -s eval -v
cargo test -p nosh-cli --locked
```

Python 自测用固定夹具、正反例和脚本化 PTY/CLI 子进程覆盖驱动、审批、超时、清理、判定和报告；新增项目用真正的离线编译/测试验证，不用 echo 成功的假工具，运行自测也需要上述完整工具链。现有 CI 为无模型测试准备 Node 22；Rust 回归覆盖观测转发及错误。它们不能替代真实模型基线。`eval/results`、大日志和 Python 缓存忽略入库。
