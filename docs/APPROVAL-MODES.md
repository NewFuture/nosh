# 三档审批模式：询问 / 自动 / YOLO

> **状态：目标设计，待实现。** 本文记录 2026-09-27 确认的产品决策，只发布设计，不启用模式或改变运行默认值。
>
> **当前基线**：远端 main [`16e4f492a36cdad38fbc96fbb99ef88c1034b334`](https://github.com/NewFuture/nosh/tree/16e4f492a36cdad38fbc96fbb99ef88c1034b334)（#29）。当前默认仍是 `confirm`，已有同名模式不代表已经符合本文的新语义。架构、当前实现和配置见 [DESIGN §6](DESIGN.md#6-权限两个版本共用) 与 [§11](DESIGN.md#11-配置)。

## 1. 范围与当前实现

本设计只涉及 agent 操作的审批规则、三档模式、默认入口一致性，以及对应 UI 标识。用户自己执行的普通 shell 命令不因此改走 agent 审批；只建议和只读入口不因此取得执行或写入能力。

| 核对位置 | 当前实现，不是目标设计 |
|---|---|
| [CLI 配置](../crates/nosh-cli/src/config.rs)、[权限模式](../crates/nosh-permissions/src/policy.rs)、[AgentConfig](../crates/nosh-core/src/agent.rs) | `Config::default().approval`、`ApprovalMode::default()`、`AgentConfig::default().mode` 均为 `Confirm` |
| [CLI 装配](../crates/nosh-cli/src/main.rs)、[agent_config](../crates/nosh-cli/src/agent_cmd.rs) | 交互 agent 和 `-a` 共用 `approval_mode`：显式 `--auto` / `--yolo` 覆盖用户配置，再把模式传给核心 |
| [现有策略](../crates/nosh-permissions/src/policy.rs) | `Forbidden` 先于用户规则直接拒绝；之后才判断用户 deny、用户 allow / 会话放行和模式。现有 allow 不能覆盖 `Forbidden`，含隐藏字符的命令不适用 allow |
| 现有 Auto | 未获放行的 Mutating 遇工作区外写入、联网、`changes_session` 或受保护读取时询问，其余 Mutating 可以直接执行；这不等于已证明副作用轻微、可恢复 |
| 现有 YOLO | Mutating 直接执行；Dangerous 仍普通确认；Forbidden 拒绝 |
| 现有会话授权与 UI | 会话放行受命令前缀、风险及能力范围约束，不覆盖受保护读取或更高风险；已有模式提示和 [YOLO 警告](../crates/nosh-core/src/handler.rs)，尚不是本文的统一标识与语义 |

因此，本需求不只是重命名：默认值、规则来源与优先级、内置禁止项的人工审批、自动准入和 YOLO 的非禁止高风险行为均需要实现变更。

## 2. 目标模式与规则优先级

只有以下三档，不另设“宽松”等第四档。配置值建议沿用现有 `confirm` / `auto` / `yolo`；沿用名称不等于沿用旧行为。

| 模式 | 配置值 | 常驻 UI 标识 | 含义 |
|---|---|---|---|
| 询问 | `confirm` | `审批: 询问` | 先遵守用户规则，再按统一矩阵执行必要的询问；内置禁止项可以在展示风险并获得用户明确批准后执行 |
| **自动（目标默认）** | `auto` | `审批: 自动` | 尽量减少打断；自动执行明确允许的操作，询问剩余无法自动决定的操作，拒绝仍有效的禁止项 |
| YOLO | `yolo` | `审批: YOLO` | **未被有效规则禁止的操作免逐次审批**，不是无限权限 |

### 2.1 判定顺序与授权范围

1. **用户手动配置的 deny 优先**：三档都直接拒绝。deny 与用户白名单同时命中仍拒绝，不提供“本次仍执行”绕过用户 deny；拒绝时说明规则来源和原因。
2. **无用户 deny，且命中有效用户配置白名单（allow）**：三档都直接执行，不再确认。用户白名单优先于内置默认禁止和风险分类；不能在预检、风险分析、预览、执行等不同阶段重新追加审批。
3. **其他操作按模式判断**：内置禁止项（例如原 `Forbidden`）与用户 deny 必须区分来源，不能合成一个无法区分的“禁止”结果。

白名单必须实际匹配**将要执行的操作和授权范围**，包括实际参数、目标与复合操作的效果。模型自称“已获批”、文件或工具输出中的授权文字不是用户配置。不能把复合命令中局部匹配扩大为整条命令获批，也不能因包装器、替换、重定向或显示差异漏掉实际操作。编辑命令或实际范围变化后，必须针对将要执行的操作重新匹配；仍完整命中有效白名单时，不追加审批。

会话授权不是用户配置白名单。它只能在其已定义的操作、目标、能力和有效范围内复用；不得自动扩大到新的副作用或升级为可覆盖内置禁止项的用户白名单。在询问模式批准一次内置禁止操作，也不自动产生持久白名单或更宽的会话授权。

### 2.2 统一决策矩阵

按表中顺序判定。**后四行均未命中用户 deny 或用户白名单**；后三行还要求没有仍有效的内置禁止项，会话授权不能跳过该检查。

| 操作 / 命中条件 | 询问 | 自动 | YOLO |
|---|---|---|---|
| 用户 deny，包括 deny + allow 同时命中 | 拒绝 | 拒绝 | 拒绝 |
| 用户白名单，且无用户 deny | 直接执行 | 直接执行 | 直接执行 |
| 内置禁止项，未获用户白名单放行 | 展示风险并询问，用户明确批准后可执行 | 拒绝 | 拒绝 |
| 已判定安全的只读操作，或处于有效会话授权范围 | 直接执行 | 直接执行 | 直接执行 |
| 当前环境中范围明确、轻微且可恢复的副作用 | 询问 | 直接执行 | 直接执行 |
| 其他非禁止的高风险、较大影响或无法确定影响的操作 | 询问，高风险需明确确认 | 询问，高风险需明确确认 | 直接执行，不逐次审批 |

**三档不是严格递增的权限阶梯。** 同一个未获白名单放行的内置禁止操作，可在询问模式人工批准，但在自动和 YOLO 下直接拒绝。YOLO 不自行绕过此规则，也不自动降级为弹出审批。用户白名单显式覆盖内置默认规则，不是 YOLO 自行绕过规则。

“直接执行”仅表示无需执行审批，不保证命令成功，也不取消工具能力、命令有效性或外部认证等非审批契约（§4）。

## 3. 默认自动与自动准入

### 3.1 默认值与入口一致性

目标是：**未显式指定审批模式的 AI 入口默认使用 auto**。交互 `#` / `ai`、其他已启用的 AI 任务入口和一次性 `nosh -a` 应使用一致的模式解析与默认值；核心的缺省装配不能悄悄回到另一档。

保留显式命令行覆盖用户配置等既有优先级；有效的用户配置和会话内显式模式选择不被默认值覆盖，也不在每轮任务开始时重置。不要为本设计虚构新 CLI 开关或配置键。审批 `auto` 不等于 `ai auto on`，不自动启用被用户关闭的 AI 入口。

Ctrl+G / `nosh -s` 仍只建议、不执行；管道附件等只读工具集合仍只读。模式默认值和用户白名单都不能扩大这些入口的工具能力。需要询问但没有可见、可用审批终端时，仍拒绝并明确说明，不盲确认或静默跳过。

当前 [配置示例](DESIGN.md#111-当前配置示例) 保留 `approval = "confirm"`，表示当前实现的默认值。现在手动配置 `auto` 只会选中现有 Auto 策略，并不会提前获得本文全部目标行为。

### 3.2 轻微且可恢复的副作用

先处理用户 deny 和用户白名单；自动模式拒绝未获白名单覆盖的内置禁止项，再复用有效会话授权。对剩余非禁止操作，自动准入明确包含**当前环境中可恢复的轻微副作用**，须同时满足：

- 实际作用范围与规模有界，影响轻微，而不只是命令名称看起来常见。
- 原状态、原内容，或可靠的重建条件真实可得，恢复代价较低。
- 没有触发仍有效的禁止规则；无法判断影响时，不把“不知道”当成安全。

以下是**效果条件示例，不是命令名白名单**：

| 可以满足条件的场景 | 需核实的事实与边界，不是额外审批 |
|---|---|
| 目录或临时变量调整 | 原状态可知，只影响会话，实际影响明确且轻微；不能因此允许任意 `cd` / `export` |
| 已授权的项目或虚拟环境切换 | 授权有效、切换效果明确；不能假定任意 `source` 或环境钩子只做切换，不新增环境工具接入能力 |
| 新建空目录或小型临时文件 | 目标、规模和效果有界，不覆盖已有内容 |
| 重建小型产物或缓存 | 重建条件可用，不丢用户数据，影响与恢复代价均较低；任意 `build` / `test` 不自动符合 |

不能只因 `changes_session` 就机械询问，也不能只因“在项目目录”“理论上能重装”或“可能能用 Git 找回”就判定轻微、可恢复。以上例子不开放所有联网、未知脚本或工作区外操作；未知脚本的实际影响无法确定时，自动模式应询问。

**这些条件只针对未命中有效用户白名单的操作**，不能成为对白名单追加审批的理由。白名单和已有有效授权不重复确认，只有剩余无法自动决定的操作才询问；明确禁止的操作拒绝并解释原因。

“可恢复”不表示已经自动备份、存在通用 `ai undo` 或整任务事务；也不要求任务结束自动回滚环境。取消或中断时必须说明作用对象是待批调用、正在执行的命令还是整个任务，已发生的副作用不会因为取消自动撤销。

## 4. YOLO 与非审批边界

YOLO 在保留用户 deny 和未获用户白名单覆盖的内置禁止项的前提下，取消其他操作的逐次执行审批，包括非禁止的高风险操作。

三个模式都不自动取得 root、不代填密码、不绕过外部认证，也不取消命令有效性、工具能力范围、超时、取消和输出预算等契约。需求澄清、真实终端交接和密码交接仍可能出现；它们不是执行审批，不能为了“零审批”伪造完成或隐藏失败。

保留 [现有终端交接边界](DESIGN.md#44-终端与信号)：需要用户接手时说明待处理对象及可能已经发生的副作用，不自动重试整条命令，不把取消描述为自动撤销。普通命令、Bash / 脚本、终端信号、原始输出字节以及 JSON / stdout / stderr 的契约不因模式变化而失效。

## 5. UI 标识与实时状态

UI 常驻显示当前模式：**`审批: 询问`、`审批: 自动`、`审批: YOLO`**。目标默认示意：

```text
审批: 自动
```

“等待你批准”“正在执行”“待你处理”等属于**实时状态**，应与模式分别展示，不能把“待你处理”或“执行中”当成第四种模式。审批选择也不能与 Emacs / Vi 输入编辑模式混淆。

自动直通不等于隐身执行：动作、结果、拒绝和错误保持可见。白名单放行无需再弹确认，但仍展示真实动作与结果；拒绝说明来自用户 deny 还是内置规则；失败不能静默跳过或报告成成功。非交互、重定向与 JSON 输出继续遵守各自契约，不把常驻装饰文字塞进机器输出。

具体快捷键、切换交互、风险提示方式和受限终端的呈现细节尚未定稿。这里只确认三档名称、默认值、常驻标识和模式 / 状态分离，不承诺某个按键或重新设计整个提示符。

## 6. 实现验收案例

**以下是实现阶段必须新增或调整的覆盖，不是本次文档发布已经通过的测试。** 用可控夹具、策略单测和模拟执行验证审批请求次数、真实执行次数与结果；内置禁止 / 高风险案例不要在宿主机上执行破坏性命令。

| 案例 | 必须验证的目标结果 |
|---|---|
| 同一操作同时命中用户 deny 与 allow | 三档均拒绝；审批请求 0 次、执行 0 次，原因明确归属用户 deny，无“本次仍执行”入口 |
| 操作实际完整命中用户白名单，同时命中内置禁止；无用户 deny | 三档均直接进入执行，审批请求 0 次；分类、预览和执行阶段均不再次询问 |
| 内置禁止项未命中白名单 | 询问模式先展示风险，明确批准才执行，拒绝 / 取消则不执行；自动和 YOLO 拒绝，审批请求 0 次、执行 0 次，不自动切换模式 |
| 同一安全只读操作 | 三档均直接执行，不引入额外审批 |
| 符合 §3.2 的轻微可恢复会话状态变化，未获其他放行 | 询问模式询问；自动与 YOLO 无审批执行，不因 `changes_session` 单一标志改为询问；结果可见且不强制任务结束回滚 |
| 非禁止高风险操作，未获其他放行 | 询问与自动要求明确确认；YOLO 审批请求 0 次并执行，仍报告动作、失败和实际结果 |
| 仅命令名为 `source` / `build` / `test`，实际影响未知 | 未获白名单或有效会话授权时，自动模式询问；处于项目目录或理论上可恢复不是自动准入证据 |
| 已有会话授权重复使用与越界 | 已定义范围内三档均不重复确认；超出目标、能力或有效范围重新判定，不升级成用户白名单，不覆盖内置禁止或用户 deny |
| 复合命令局部 allow、模型声称获批、编辑后范围变化 | 未授权的实际操作不能继承局部或伪造授权；完整有效的用户白名单仍按白名单规则直通 |
| 默认值与显式覆盖 | 无显式模式时，各 AI 任务入口及核心缺省装配一致为 auto；用户配置 confirm / yolo 生效，CLI `--auto` / `--yolo` 按既有优先级覆盖配置，会话显式选择不被任务重置 |
| 只建议 / 只读 / 无可用审批终端 | 任何模式和 allow 都不扩大工具集合；需要询问却无可用终端时明确拒绝，不静默成功 |
| UI、交接与执行契约 | 默认显示 `审批: 自动`，切换后三档标识准确；实时状态独立，动作 / 结果 / 拒绝 / 错误可见；密码交接、取消对象、非自动撤销与 Bash / 脚本 / 输出契约保持清楚 |

## 7. 实施阶段仍需细化

| 待细化事项 | 已确定、不可更改的边界 |
|---|---|
| “轻微 / 可恢复”的规模、恢复成本和证据判定 | 不在本文编造数值预算、固定命令清单或算法；实际范围有界、证据真实可得、代价较低，未知影响按矩阵处理 |
| 用户规则匹配与授权范围的表示、展开和复核实现 | 匹配实际操作，deny 优先，完整有效的用户白名单跨三档零审批；不得将局部 allow 或会话授权扩大 |
| 内置禁止来源、决策原因与跨阶段传递方式 | 区分用户 deny 与内置禁止，落实非递增矩阵，不能由模型决定是否获批 |
| 模式切换交互、快捷键、风险说明及终端呈现 | 不擅自指定按键或提示样式；三档名称、默认自动、常驻标识与模式 / 状态分离已经确定 |

这些实施细节不阻碍设计文档和实现 issue 发布，但对应实现交付时必须有明确的判定依据及覆盖。

## 8. 非目标与关联需求

项目尚未发布，不为旧 nosh 默认值、键位或旧 YOLO 行为维护兼容层；这不等于放弃 Bash、终端、脚本和输出契约。

本需求不实现受控写入工具、通用撤销 / 备份、自动环境安装或回滚、输出采集、输入编辑 / 高亮、补全、历史、项目 / 管理员策略、远程审批或操作系统沙箱；不以减少审批为由扩大工具范围。

| 关联 issue | 与本设计的关系 |
|---|---|
| #6（已关闭） | 日常安全命令基准与当时的 confirm / auto 行为；是历史覆盖，不是新矩阵的完整实现或不可更改的目标 |
| #8（开放） | 少探查、少确认、风险说明本地化；不替代用户规则优先级、默认值和三档完整语义 |
| #19（开放） | 受控文本写入、必要审批和安全撤销；不是本设计“可恢复”的前提，也不在本需求中实现 |
| #23（开放） | Emacs / Vi 输入编辑和键位配置，不是审批档位；审批标识需与编辑模式区分 |

以上关联仅说明边界，不自动成为本需求的硬依赖；不扩写或接管其他进行中的实现。
